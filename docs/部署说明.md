## 4. ADM1jl 求解器后端（换到 Julia，实测 5.8×）

### 到底换了什么
ADM1jl 是 **35 状态**的单罐模型（自带求解器），PyADM1ODE 是 **41 状态** ADM1da + 厂站框架。
两者状态维度和模型假设都不兼容：把 41 状态塞进 ADM1jl 的 `ADM1sol` 是维度错误，而改用它的
35 状态模型会丢掉整个厂站框架（多级消化器、进料调度、能源、传感器）。所以换的是**数值层**：

- 41 状态右端项（`ADM1.ADM_ODE`）逐项移植成 Julia：`pyadm1/core/julia/adm1da.jl`
- 用 **`Rodas4P`** 积分——就是 ADM1jl 处理 ADM1 时调用的那个 Rosenbrock 方法
- 求解器以上的一切（组件、配置器、pH/VFA/TAC、JSON 输出）原封不动

完整设计与限制见 `PyADM1ODE/webdemo/README.md`。

**为什么不是"Julia 当积分器、RHS 留在 Python"**：剖析显示每次 RHS 调用 35 µs，跨语言封送还要
再加 10–50 µs，那样只会更慢。RHS 必须也跑在 Julia 里，换求解器才有意义。

### 怎么开
```powershell
$env:PYADM1_SOLVER = "adm1jl"    # 本次会话生效
setx PYADM1_SOLVER adm1jl        # 永久（只影响新开窗口）
$env:PYADM1_SOLVER = "scipy"     # 切回默认
```
默认仍是 scipy，所以现有脚本、notebook、测试的行为完全不变。

### 实测数据
同一场景（`examples/01`，150 天，dt=1.0，5 次取中位数）：

| 后端 | 耗时 |
| --- | --- |
| scipy BDF | 0.896 s |
| ADM1jl / Rodas4P | 0.155 s |
| **加速** | **5.8×** |

150 天轨迹偏差：沼气 1.8e-06、CH₄ 2.7e-06、pH 6.1e-07（相对值）。
两条后端的示例输出**逐字节一致**。
一致性测试 9 条：RHS 逐点吻合 < 1e-9，单日积分与 scipy 吻合到 1e-5。

### 代价（用之前先知道）
5.8× 说的是**预热之后、只算积分本身**。冷启动完全是另一回事，实测（同一套机器）：

| 冷进程里的开销 | 耗时 |
| --- | --- |
| `import juliacall` | 2.13 s |
| 加载 Python 侧模块 | 0.82 s |
| 加载 Julia 模块 | 1.56 s |
| 首次调用编译（warmup） | 6.39 s |
| **首次有用计算之前合计** | **10.94 s** |

所以**冷进程跑一个完整示例**：scipy 1.71 s，adm1jl 11.12 s——**单次短仿真反而慢 6.5 倍**。
只有长仿真、参数扫描、批量/标定这类"一个进程里跑很多次"的场景才划算。

- **首次调用编译约 6.4 s**：Julia 按函数类型即时编译。`adm1_julia.warmup(adm1)` 可预先付掉。
- **进程启动多约 4.5 s**：加载 juliacall + Julia 运行时。
- **模型写了两份**（Python 一份、Julia 一份）：改化学必须两边都改，
  `tests/unit/test_core/test_adm1_julia.py` 就是拿来做对账的。
- `AdaptiveODESolver`（scipy 那个自适应容差包装）没有 Julia 等价物；`max_step` 会传成 `dtmax`，
  两后端内部步长可比。

#### 启动耗时：一次踩坑记录

Julia 启动慢不是必然的，这台机器上是**原生代码缓存没生成**。实测：

| 状态 | 冷启动 | 拆分 |
| --- | --- | --- |
| 只有 `.ji`、没有原生缓存 | **31.7 s** | import 12.1 + 加载模块 13.4 + JIT 6.2 |
| 生成原生缓存后（现在） | **9.5 s** | import 1.8 + 加载模块 2.1 + JIT 5.7 |

`~/.julia/compiled` 里原本 **0 个原生缓存 DLL**，等于每次启动都在从头编译 OrdinaryDiffEq 全家。
跑一次 `Pkg.precompile()` 之后出现 **164 个 DLL**，冷启动从 31.7 s 掉到 9.5 s。

`_setup_julia.py` 里本来就有 `Pkg.precompile()`，但它会**静默地不产出原生缓存**（只写 `.ji`）。
现在脚本末尾加了核对：

```
[check] native code caches under C:\Users\...\.julia\compiled: 164
```

**数字为 0 就说明缓存没生成，重跑一次脚本。哪天启动又变慢，先看这个数字。**

网页这边不用等：服务一启动就把 Julia 丢到后台线程预热（`_bootstrap_julia`），
所以**点按钮不会触发编译**。实测重启后第一次对比 7.8 s、第二次 1.2 s。

#### 方案 A：把 ADM1da 做成预编译包（已实施）

`adm1da.jl` 原来是运行时 `include` 的字符串，Julia 不会为它缓存原生代码。
现在它是 `pyadm1/core/julia/PyADM1Julia/` 下的**真包**，用 `PrecompileTools` 跑一段
真实积分作为工作负载，把类型特化烘进 pkgimage。

生成器：`python pyadm1/core/julia/gen_package.py`（改了 `adm1da.jl` 或 `PARAM_FIELDS`
之后要重跑；桥接层会断言两边的字段顺序一致，不一致直接报错并提示重跑）。

两个实现细节值得记下来：

- 入口函数拆成**薄包装 + typed core**。juliacall 传进来的是 `PyArray`，不拆的话每个新参数
  类型都会把整个求解器重新特化一遍，工作负载覆盖不到。
- 工作负载**不能包在 `try/catch` 里**——`@compile_workload` 对 try 块内的代码不保证缓存。

效果（同一台机器，实测）：

| 阶段 | 预编译前 | 预编译后 | 方案 A 之后 |
| --- | --- | --- | --- |
| `import juliacall` | 12.1 s | 1.8 s | 2.2 s |
| 加载模块 | 13.4 s | 2.1 s | 2.2 s（`using PyADM1Julia`） |
| 首次编译 | 6.2 s | 5.7 s | **1.8 s** |
| 冷启动合计 | **31.7 s** | 9.5 s | **6.3 s** |
| **重启后立刻点按钮** | — | **6.24 s** | **0.41 s** |

剩下那 1.5 s 是 **PythonCall 的 `PyArray → Vector{Float64}` 首次转换**，属于另一个包的
代码，预编译覆盖不到。但它在服务启动时就被后台预热掉了（`_bootstrap_julia` 里多调了一次
`warmup()`），所以**点击路径上不再有它**——这就是 6.24 s 掉到 0.41 s 的原因。

顺带一提：纯 Julia 侧的 `_integrate_step` 首次只要 **0.14 s**，说明包的预编译是有效的，
剩下的开销全在跨语言边界上。

## 5. 可视化操作平台（本地网页 demo）

一个跑在本机的单页仪表盘：左边调工艺和进料，右边看产气 / pH / VFA 曲线，
一键切换求解器、导出 CSV。仓库里在 `PyADM1ODE\webdemo\`。

### 怎么开

双击 `pyadm1-web.bat`（会自动打开浏览器），或者手动：

```powershell
cd "<repo>/PyADM1ODE"
.\.venv\Scripts\python.exe webdemo\app.py
```
→ 打开 http://127.0.0.1:8848 。关掉那个命令行窗口服务就停。换端口加 `--port 9000`。

### 能做什么

| 能力 | 说明 |
| --- | --- |
| 进料配比 | 13 种基质任选，条数随意增删，实时汇总总进料量 |
| 工艺参数 | 温度、液体体积、气室体积、传质系数 k_L a（滑块 + 输入框联动） |
| 仿真设置 | 天数、步长 dt，以及 scipy BDF / ADM1jl Rodas4P 切换 |
| 结果 | 6 张指标卡 + 4 张交互曲线（可缩放、悬停读数）+ 工艺示意图 |
| 对比 | 同工况跑两求解器，给耗时、加速比、逐曲线最大相对偏差 |
| 导出 | 10 列时间序列 CSV |
| **三通道分步**（`/trace`） | 三种积分器并排，各跳各的步，共用时间轴 |
| **组件系统**（`/system`） | 两级厂站的模块网络，物料 / 沼气 / 能量三通道流动 |

演示小技巧：`http://127.0.0.1:8848/?compare=1` 打开后自动跑一次对比，省得当场点。

### 求解引擎（/engine）— 自研复刻

`http://127.0.0.1:8848/engine`。视觉语言照 HALOFLUX 复刻（编织光场、环形微数据卡、
多层向外光束、节拍时钟、自动运镜、辉光），但**代码全部自己写**（`static/engine.js`，
原生 Canvas、零依赖），没有引入或改写上游源码，因此不受其许可限制。

画面每个元素都由真实求解步驱动：

- 节拍 = 求解器真实接受的一个步
- 光束长度 = 该角度对应状态的 |dy/dt|（按 p95 归一化）
- 圆环 41 张卡片 = 状态名 + 真实数值 + 结构条 + 火花线
- 顶部 KPI / 底部四块图 = 时间、步数、产气、pH、CH₄、状态量、步长

`?still=1` 冻结时钟（画面继续重绘，截图稳定）。

### 三通道分步（/trace）

`http://127.0.0.1:8848/trace`。同一 ADM1da 方程、同一组容差，三种积分器各跑一遍：

| 通道 | 150 天实算步数 |
| --- | --- |
| scipy · BDF | 2553 |
| scipy · LSODA | 7107 |
| ADM1jl · Rodas4P | 2057 |

三者终值完全一致（沼气 2136.5 m³/d、pH 7.3271），但步数差 3.5 倍。每列下方是**累计步数曲线**，
斜率越陡说明该求解器在这段时间越费劲；温度阶跃那一段三条曲线同时变陡。

每列中间是 41 状态环：微面板高度 = 状态值，向外光束 = |dy/dt|，中心 = 产气速率。
第三通道用 LSODA 而不是 torch——torch 是另一个导数实现、跑的仍是同一个 BDF，
步序列会和第一列重合，还要多装 2.5 GB。

### 组件系统 / 三通道流动（/system）

`http://127.0.0.1:8848/system`。用 `PlantConfigurator` 搭出两级厂站：

```
进料 → 水解罐 → 主发酵罐 → 储气 1/2 → CHP → 电网 / 水解加热 / 主罐加热
```

连线按通道着色（物料 / 沼气 / 电能 / 热能）、按该时刻真实流量流动（对数映射），
线上标的就是当时的数值。

两点要说明：**CHP 稳态只有约 22 kW（额定 500）**——储气罐按"上一步消耗量"回馈供气，
CHP 要多少给多少，于是稳定在低负荷，这是库里的控制逻辑，没有改；
**储气罐显示的是"→ CHP 流量"而不是存量**——罐容 1000 m³ 而进气 2000 m³/d，一天内灌满即泄，
存量恒为 0。

操作：空格播放/暂停、可拖时间轴和切 0.5–4× 速度；`?t=42` 直接跳到第 42 天。
视觉构图参考 [HALOFLUX](https://github.com/Ryder191/haloflux)（非商业），实现是自己写的 Canvas。

### 实现要点

- **后端只算不画**：`app.py` 建厂 → 积分 → 返回 JSON，图表全在浏览器里；
  plotly.js 用**本地文件**（从 pip 的 plotly 包里取的），不走 CDN，断网也能开。
- 两个求解器在同进程切换靠 `set_solver_backend_override()`，不去改环境变量。
- 对比模式**先预热 Julia 再计时**，否则首次编译那 6 秒会算进加速比，
  显示成 0.05× 这种误导性数字（这个坑我踩过并修了）。
- API 清单和实现细节见 `PyADM1ODE\webdemo\README.md`。

### 局限

单进程同步执行，一次只能跑一个仿真（点完按钮要等状态条变"完成"）；
没有用户系统、数据库、任务队列。要多人用或批量跑，得把仿真挪进队列 + worker。

## 6. 配套包（calibration / estimation）

两个官方配套仓库放在仓库根目录下，装进**同一个 venv**（editable 方式）：

| 包 | 版本 | 位置 | 实测 |
| --- | --- | --- | --- |
| `pyadm1ode-calibration` | 0.2.8 | `PyADM1ODE_calibration` | ✅ **287 passed, 5 skipped** |
| `pyadm1ode-estimation` | 0.2.5 | `PyADM1ODE_estimate` | ✅ **311 passed, 1 skipped** |

两个都是库，没有命令行入口。用法跟在 PyADM1ODE 里一样，但导入路径不一样：

```python
# calibration：顶层就导出了主要类
from pyadm1ode_calibration import Calibrator, CalibrationResult, CSVHandler, Database

# estimation：顶层 __init__ 不导出东西，要进子模块
from pyadm1ode_estimation.estimation import filters, observer, twin, sensors, fusion
from pyadm1ode_estimation.estimation import pinn        # 物理信息神经网络（需要 torch）
```

`estimation` 的子模块对应它支持的几件事：`filters`（EKF/UKF）、`observer`、
`twin`（数字孪生）、`sensors` / `observation_model`（观测模型）、`fusion`（多源融合）、
`measurement_calendar`（采样计划）、`pinn`（PINN 估计器）、`reference` / `realism`（合成基准）。

### 装法上有个必须绕开的坑

两个包都把 `pyadm1` 声明成 **git 直连依赖**：

```
pyadm1 @ git+https://github.com/dgaida/PyADM1ODE.git
```

直接 `pip install -e .` 会让它去 GitHub 拉一份 pyadm1 **覆盖掉本地的 0.6.2**——
而我们改过的 `adm1_julia.py`、`core/julia/`、`webdemo/` 在那一份里全都没有，
等于把前面所有工作废掉。

所以必须 `--no-deps`，缺的库单独补：

```powershell
cd "<repo>"
$env:VIRTUAL_ENV="PyADM1ODE\.venv"
uv pip install -e .\PyADM1ODE_calibration --no-deps
uv pip install -e .\PyADM1ODE_estimate    --no-deps

```

#### `demo_calibration.py` —— 反演一个动力学参数

思路是"先造真值、再假装不知道"：把 `k_hyd_ch` 设成 10.0 跑出 Q_ch4 当实测，
再复位成默认 4.0，让标定框架把它反推回来。实测输出：

```
实测 Q_ch4 均值 ≈ 898.3 m3/d（30 天，真值 k_hyd_ch=10.0）
  方法      : nelder_mead   success=True   迭代=15
  初始      : k_hyd_ch = 4.00   -> RMSE  127.837 m3/d
  校准结果  : k_hyd_ch = 10.00  -> RMSE    0.001 m3/d
  相对误差  : 0.0%
  Q_ch4_r2  : 1.0000
  apply_calibration() 之后 kinetic[k_hyd_ch] = 10.000
```

核心 API 只有三步：

```python
measurements = MeasurementData(df)        # df 里要有 Q_sub_0..n 进料列 + Q_ch4 目标列
cal = Calibrator(plant, verbose=False)
result = cal.run_initial_calibration(measurements, ["k_hyd_ch"],
                                     method="nelder_mead", objectives=["Q_ch4"])
cal.apply_calibration(result)             # 写回模型
```

#### ⚠ 参数名必须和 `ADM1._kinetic` 对上（重要）

`create_default_bounds()` 给了 41 个参数名，但 **pyadm1 0.6.2 的 kinetic 字典里只有 33 个**。
对不上的 8 个会**静默失效**——写进 `_calibration_params` 就没人读，仿真结果一点不变，
看起来就是"校准没用"。实测对照：

| 包里的名字 | 实际应写 |
| --- | --- |
| `k_dis` | `k_dis_PS` / `k_dis_PF`（按基质分了两个） |
| `k_dec_X_su` … `k_dec_X_h2`（7 个） | `k_dec_su` … `k_dec_h2` |

其余 33 个（`k_hyd_*`、`k_m_*`、`K_S_*`、`Y_*`、`k_dis_PS/PF`）可以直接用。
写脚本前先跑一句自检：

```python
assert PARAM in plant.components["main_digester"].adm1._kinetic, f"{PARAM} 不会生效"
```

#### `demo_estimation.py` —— UKF 状态估计

孪生实验：真值与滤波器两个装置预热到同一状态，滤波器只拿 `Q_gas` / `Q_ch4` / `pH`
（带噪声），跑 16 小时。实测：

```
滤波器   : 41 个 ADM1 状态 + 2 个进料通道（共 43）
观测     : ['Q_gas', 'Q_ch4', 'pH']
状态量相对误差（最后 8 小时）
  纳入统计 : 38/41 个状态（剔除 |真值|<1e-4 的近零量）
  中位相对误差 : 2.64%
```

核心 API：

```python
ukf = build_ukf(plant, "main_digester",
                substrates=[InputSpec("maize", 0, 11.4), InputSpec("swine", 1, 6.1)],
                sensors=("q_gas", "q_ch4", "ph"))
for k in range(N):
    ukf.predict(dt)
    ukf.update({"Q_gas": ..., "Q_ch4": ..., "pH": ...}, t=(k+1)*dt, equilibration_dt=dt)
```

`build_ukf` 把六步装配（41 通道 spec → 观测模型 → 过程模型 → SR-UKF → 快照 → reset）
打包成了一次调用；`ukf.update()` 返回 `EstimationStep`，带 `x_hat / y_pred / y_std /
innovation / nis`，可以直接拿来做残差监控。

#### 关于收敛速度（如实说明）

同一个脚本里，**进料量通道在 16 小时内几乎没被拉动**（先验 6.84 → 估计 6.85，
真值 11.40）。这不是 bug：消化器把进料扰动缓冲掉了，产气对进料有滞后，
短窗口内这个通道接近不可观测。要它收敛得加长窗口（数十天量级）或调大
`InputSpec(process_noise_std=...)`。

**成本也要有数**：每个小时一次预测 = 43 状态 → 87 个 sigma 点，每个点都要推进一遍
机理模型，约 3 秒/步。16 小时 ≈ 50 秒。别把窗口开到几百小时。

## 7. 三个已知坑（已确认，不是环境装坏）

**① 中文 Windows 控制台编码 → `UnicodeEncodeError: 'gbk' codec`**
示例会打印 `m³`、`°C` 等字符，GBK 打不出来会直接崩掉整个脚本。
解决：跑之前 `$env:PYTHONUTF8 = "1"`（`pyadm1-env.bat` 已自动设好）。

**② `pyadm1-simulate` 命令不可用（上游 bug）**
`pyproject.toml` 里声明了入口点 `pyadm1-simulate = "pyadm1.cli:main"`，
但仓库里根本没有 `pyadm1/cli.py` 这个模块，所以一调用就是
`ModuleNotFoundError: No module named 'pyadm1.cli'`。
这不影响任何库功能，用 `python main.py` 或 `examples\*.py` 即可。
（要长期用可以自己补一个 `cli.py`，或者给上游提 issue。）

**③ 别往 .bat 里写中文**
`pyadm1-env.bat` 是纯 ASCII 的，这是故意的。cmd.exe 在一个 UTF-8 编码的批处理里
执行过 `chcp 65001` 之后，会按**字节偏移**去定位下一行，中文一个字 3 字节，行就被
切错位——`rem` 注释里的中文会被当成命令执行（实测会报
`'…活' is not recognized as an internal or external command`），整个脚本行为不可预测。
中文说明都放这份 .md 里，脚本只留英文。
